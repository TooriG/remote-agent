# アーキテクチャ全体の再設計

対象は共通クライアント、デスクトップ、iOS、Android、Host との通信・保存境界を含む全体。
過去の計画は制約にしない。段階は実装順序であり、作業対象を限定するものではない。
既存の操作、表示、文字選択、スクロール位置、オフライン復旧を維持する。

## レビュー結果

「表示に必要な状態だけを観察する」「部品が自分の状態と操作を所有する」方向を採用する。
ただし、元の案には次の修正が必要。

- 状態の分類だけでは観察の分離にならない。別会話の更新、下書きの変更、RPC の開始・終了が、
  無関係な一覧・会話・ワークベンチの再計算を起こさない購読経路まで実装する。
- 操作状態は内容と別の責務。操作マップを五つに分散させると分類規則と横断処理が増える。
  一つの操作状態を保ち、表示側は必要なキーの phase を参照する。
- 共有参照の同一性は内容の同一性とは異なる。変更のない入力で参照を維持し、
  会話 ID・下書き ID ごとの値を選ぶ。UI 固有の表示値の比較まで機械的に廃止しない。
- 重い射影を状態遷移と同じ直列ワーカーに載せると、入力・キャンセル・再接続を待たせる。
  独立した実行経路で最新の入力に集約し、入力が変わった古い結果を採用しない。
- 複数ペインでは選択だけでなく購読の寿命、操作の失効条件、ワークスペースも独立させる。
  Store と会話・下書きのデータは共有する。
- 全 Snapshot を読むメソッドへの転送を増やしても依存は減らない。
  判断・変換には具体的な値を渡し、副作用は状態・接続を所有する場所に集める。
- iOS の VStack を LazyVStack に交換するだけでは、文字選択、文字計測、末尾追従、
  過去履歴の追加時の位置保持を保証できない。既存の受け入れ条件を保持して実装する。
- 過去の開発ログは遅い区間の存在を示すが、原因や改善量は示さない。
  GPUI の render、prepaint、paint、射影の実行回数を分ける。
  paint 回数とレイアウト変更回数の一致は完了条件にしない。
- CompositionLocal の利用だけで Android の全ツリーが再構成されるとは断定しない。
  実際の state の読み取り位置と更新経路を確認する。

## 目標の責務

### 共通状態と購読

一つの整合した状態遷移と一回の確定を保つ。
接続、カタログ、一覧、会話、入力、ファイル、ナビゲーション、ターミナル、取り込み、操作を
責務ごとの型で表し、変更報告は型の定義に結びつける。
購読者は中間通知に依存せず、前回受け取った状態と最新状態を比較する。
操作の世代番号は古い応答の拒否に用い、表示は必要なキーの phase を読む。
画面への入力は具体的な共有参照と小さな値から構成する。
会話と下書きは、それぞれの ID の値を選ぶ。
会話の射影・一覧の導出は core、OS 固有の描画と入力は各 UI が所有する。
汎用リアクティブ基盤、同じデータの二重管理、移行用の旧経路は残さない。

### デスクトップ

ウィンドウは配置と子同士の UI 操作の調整を所有する。
サイドバー、ヘッダー、会話、入力欄、ワークベンチ、設定、通知は、
それぞれの表示状態・入力状態・操作を所有する。
描画時に親の Context を借りる経路と、親の全体通知から全表示値を作り直す経路を削除する。
判断には必要な値だけを渡し、サイドバーと会話は表示範囲に応じて行を生成する。
アニメーションは末端で更新する。

### ペインと接続

同一 Host のサイドチャットは Store、接続、会話キャッシュ、下書きを共有する。
各ペインは独立した選択とワークスペースを持つ。
片方を閉じても他方の購読を解除せず、再接続時に開いている両方の会話を復旧する。
保存する状態は一つの明示的な射影とし、会話・下書き・設定を維持する。

### モバイル

iOS はナビゲーション・接続、一覧、会話、入力とワークベンチの観察を読み取り位置で分ける。
Android も、画面全体へ配る可変 Snapshot に表示判断を結びつけない。
両アプリの独自の会話射影の実行制御と古い更新判定を削除し、共通の表示値を使う。
iOS の長い会話は、文字選択・スクロール・履歴追加を保つ遅延描画にする。

### Host・protocol・transport

通知の順序、再同期、購読の解除、切断時の回復、保存と転送の境界を通して確認する。
protocol は純粋な共通契約、transport は通信、Host は実行・認可・資源操作を所有する。
クライアントの描画都合を Host の業務ロジックや bindings に持ち込まない。
この境界に構造上の問題があれば修正対象に含める。

## 実装順序

1. 共通状態と変更報告を整理し、desktop・Swift・Kotlin の全呼び出し元を更新する。
   旧 publication_key、全体の許可リスト、重複した変更判定を削除する。
2. ペインの選択・操作・購読の寿命を core で定義する。
   同じ Host に対する二つ目の Store と接続を削除する。
3. 共通の表示入力と射影の実行を core に集め、UI スレッドから重い計算を外す。
   最新入力を集約し、古い結果を拒否する。
4. デスクトップの状態と操作を各部品へ移し、親への観察と描画の転送を削除する。
   サイドバーを仮想化し、ウィンドウは配置と子間の操作調整に縮める。
5. iOS・Android の観察と入力の所有権を分け、共通の表示値を利用する。
   iOS の会話を既存の受け入れ条件を保つ遅延描画にする。
6. 全経路を再レビューし、重複・不要な状態・転送・旧実装を削除する。
   Host とクライアントの境界も再確認し、統合と検証を完了する。

## 検証と完了

- 文字入力、配信、別会話の更新、操作の開始・成功・失敗・再試行、画面切替を検証する。
  内容が変わらない部品では表示入力の生成と重い射影が走らないことを確認する。
- 複数ペインの下書き、同時配信、片方を閉じる操作、再接続と古い応答の拒否を検証する。
- 保存と復元、認可、通信の順序・世代など独立した境界のテストを維持する。
- 描画は render とキャッシュの再利用を区別する。OS の paint までゼロにする条件は置かない。
- 共通 Rust は対象クレートの nextest と、統合前の just unit-tests を設定済みビルダーで実行する。
  判断や状態遷移は対象を絞った cargo-mutants でも確認する。
- scripts/dev-env.sh just complexity を通す。閾値や除外による回避はしない。
- Apple のビルドとネイティブ受け入れは Native clients CI で確認する。
  計画を理由にローカル E2E や稼働中 Host の再起動を自動で行わない。
- 共通テスト成功後に main へ直接統合し、対象コミットの Portable checks と、
  対象を含む main の Native clients の成功まで確認する。

実装の契約と判断理由は所有するコードとテストの近くに置く。
この計画は完了後に削除し、作業記録として残さない。
