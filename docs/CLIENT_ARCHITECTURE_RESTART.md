# クライアント構成の再出発

作成日：2026-11-05

確認した main：`6a4ce471a`

状態：所有者の承認待ちの計画。承認後、段階ごとにブランチで実装する。

## 1. なぜ再出発するのか

これまでのリファクタリングは、重さの原因となる構造を残したまま、その構造が要求する差分判定や複製回避を一つずつ直してきた。
直近 300 コミットの件名を見ると、「Reuse」「skip」「without cloning」「Cache」で始まる変更が十数件あり、いずれも既存の判定関数や射影の内側を改めている。
その結果、症状が見つかった箇所は速くなるが、次の症状は別の判定関数から出る。

デスクトップの「ビューが全部一つ」という問題も、この繰り返しの中では直らなかった。
サイドバーや会話を別ビューに切り出した変更はあるが、それらは依然として一つの中心ビューを観察し、中心ビューの通知ごとに自分の表示値を作り直して比較している。
中心ビューに状態と描画が集まる構造そのものは残っている。

この計画は、クライアント側の構造を「表示が、描画に必要な最小の状態だけに結びつき、変化の判定を手書きしない」形に置き換える。
Host は対象にしない。
Host の会話記録は 2026-11-02 の決定（Host のイベントログと順序番号による再同期）に沿って進んでおり、本計画と独立に進められる。

判断の基準は 2026-10-04 の再設計計画と同じである。
今の不具合に必要かではなく、長く付き合う設計に含まれるべきかで判断し、含まれる要素は最も単純な形で作る。
費用は判断に入れない。

## 2. 現状の構造と、それが重さを生む仕組み

### 2.1 共通クライアント：一つの Snapshot を丸ごと発行する

Store は、入力一文字の下書き保存、配信された一トークン、RPC の開始と完了、一覧の更新、ターミナル出力のどれでも、約 45 項目を持つ `Snapshot` 全体を新しい値として発行する。
購読者は「何かが変わった」としか知らされないため、自分に関係する変化かどうかを手で判定しなければならない。

この判定が現在五か所に手書きされている。

- Store の発行判定（`publication_key`）。項目を一つ追加するたびに更新が要る旨の注記がある。
- 一覧の不変判定（`list_unchanged`）と会話の不変判定（`conversation_unchanged`、`SnapshotChanges`）。モバイル用に core が持つ。
- デスクトップの全体判定（`general_snapshot_changed`）。約 40 項目の許可リスト。
- デスクトップの各サブビューが作る表示値（`SidebarModel`、`ComposerModel`、`HeaderModel`、`WorkbenchModel`、`ConversationModel`）の `PartialEq` 比較。

判定を手書きしている限り、漏れは構造的に起き続ける。
加えて `Snapshot` には 18 ファイルにわたって 30 の `impl Snapshot` ブロックがあり、表示の射影はすべて全体型のメソッドとして生えている。
表示に渡せるより狭い型が存在しないので、ビューが全体を受け取るのは必然である。

### 2.2 デスクトップ：Desktop が状態と描画の中心にある

`Desktop` エンティティは、Store の `Snapshot` に加えて、入力欄、質問欄、ファイル編集、モデル設定、アカウント、ワークツリー、検索、ファイルブラウザ、パネル、画像ギャラリー、音声入力、選択範囲まで、すべての部品状態を所有する。
`impl Desktop` ブロックは 20 ファイルに 34 ある。

サブビュー（サイドバー、会話、入力欄、ヘッダー、ワークベンチ）は `WeakEntity<Desktop>` を持ち、次の二つの経路で Desktop に依存している。

- 観察：`cx.observe(desktop)` で Desktop の通知を受け、`desktop.read(cx).xxx_model()` で表示値を全体から作り直し、前回と比較する。会話ビューは会話の射影、サイドバーは一覧の射影、入力欄は候補と素早い設定、ワークベンチはエージェント一覧（全会話を走査する）を、Desktop が通知するたびに計算する。
- 操作：描画時に `desktop.update(cx, |_, cx| Desktop::render_xxx(model, cx))` と Desktop の文脈を借り、`cx.listener` を Desktop 上に作る。ビュー内の `cx.listener` は 73 箇所、Desktop への `update` や `upgrade` は 59 箇所ある。

このため、どの操作も「Desktop を変更して `cx.notify()`」になり、その一回の通知で五つのサブビューがそれぞれ全体から表示値を作り直し、Desktop 自身もルート、ヘッダー、ワークスペースカード、設定、エラー通知、ポップオーバーを描き直す。
表示値の比較で描画を省けても、作り直しの計算は省けない。

サイドチャットは `Mode::SideChat` の二つ目の `Desktop` であり、二つ目の Store と接続を持つ。
2026-10-04 の計画の段階 8（同じ Store の二つ目のペイン）は実装されていない。

### 2.3 デスクトップ：毎フレームの処理がルートまで届く

GPUI は、アニメーションする要素とウィンドウのルートの間にあるビューを毎フレーム描き直す。
`activity.rs` はこの性質を避けるために、スピナーをキャッシュ済み内容の上の別レイヤーで回している。
回避策が要ること自体が、ルートが不活性でないことを示している。

### 2.4 デスクトップ：サイドバーは値として作り直され、仮想化されていない

`SidebarModel` は、比較のために一覧の射影全体（各プロジェクトのアイコン PNG のバイト列を含む）を複製する。
描画は全行を `children` として生成し、仮想化していない。
一回の prepaint に 4 から 5 ミリ秒かかっている。

### 2.5 モバイル：同じ一極構造を Swift と Kotlin で再現している

iOS の `AppViewModel` は `@Published` を 16 個持つ一つの `ObservableObject` で、`snapshot` のほかに接続中タスクの辞書、転送中フラグ、通知文も同居する。
11 ファイルにわたる画面がこのオブジェクト全体を観察するため、どの `@Published` が変わっても全画面の body が再評価される。
Android は `snapshot by mutableStateOf` を `CompositionLocal` で配り、全ツリーが再コンポーズの対象になる。

iOS の会話画面は `ScrollView` の中に遅延のない `VStack` で全行を並べる。
これは 2026-10-26 の変更（`1acdd0298`）で、文字描画を表示範囲に限る計測キャッシュとネイティブ選択を保つために `LazyVStack` から置き換えたものである。
長い会話では全行のレイアウトが走る。

### 2.6 共通クライアント：重い射影の実行場所がアプリごとに違う

会話の射影（`project_conversation`）を、デスクトップは Desktop の観察コールバック内でメインスレッドで実行し、iOS は分離タスクで実行し、Android は publish の中で実行する。
2026-10-04 の計画 4.4 節は画面の表示値を共通クライアントで導出すると定めたが、実行の場所と方針は各アプリに残っている。

## 3. 目標の構成

目標は一文で言える。
**ビューは描画に必要な最小の状態の塊だけを観察し、塊の変化は共有参照の同一性で判定する。**

### 3.1 共通クライアント：Snapshot を塊に分け、塊ごとの変化を core が報告する

`Snapshot` は一つの整合した値のままとし、一つの reducer と一回の確定、一つの永続化の射影を保つ。
これは 2026-10-04 の計画 4.3 節の決定であり、変えない。

変えるのは発行の粒度である。
`Snapshot` を責任ごとの塊（それぞれ `Arc`）で構成し、確定のあとに Store が「どの塊の参照が変わったか」を報告する。
判定は塊の一覧に対する一つのマクロで行い、項目の追加は塊の定義の変更として一か所に閉じる。
2.1 節の五つの手書き判定はすべて削除する。

塊は次のとおりとする。
2026-10-04 の表を、その後に増えた項目と、変化の頻度の違いで分け直した。

| 塊 | 項目 | 分ける理由 |
|---|---|---|
| 接続 | `connected`、`epoch`、`connection_generation`、`connection_failure`、`host_name`、`host_ticket`、`host_home_directory`、`storage_scope`、`error` | 変化が稀で、ほぼ全画面が参照する |
| 操作 | `operations`、`operation_sequence`、`unconfirmed_lists` | RPC の開始と完了ごとに変わる。内容を表示するビューを巻き込まない |
| カタログ | `models`、`model_errors`、`model_preferences`、`account`、`permission_settings`、`composer_catalog`、`file_open_capabilities`、`preferred_editor` | 設定と入力欄の制御だけが参照する |
| 一覧 | `threads`、`project_threads`、`expanded_projects`、`list_query`、`activity`、`task_activity`、`project_preferences`、`archived_scopes`、`recent_chats`、`management` | サイドバーとタスク一覧だけが参照する |
| 会話 | `conversations`、`subscriptions`、`pending_submissions`、`draft_sessions`、`observed_agents` | 会話ビューは自分の `SessionRef` の `Arc<Thread>` の同一性だけを見る |
| 入力 | `drafts`、`question_drafts` | 入力欄は自分の `DraftKey` の項目だけを見る |
| ワークスペース | `workspace`、`workspaces`、`file_drafts` | ワークベンチだけが参照する |
| ターミナル | `terminals` | 既に別の所有者がいる |
| プロジェクト取り込み | `project_import` | オンボーディングだけが参照する |
| ナビゲーション | `navigation`（ペインごと、3.4 節） | 選択の変化は会話、入力欄、ヘッダーが参照する |

塊ごとの reducer や塊ごとの永続化は作らない。
作るのは、確定後の同一性比較と、その結果の報告だけである。

### 3.2 共通クライアント：画面の表示値を core が導出し、重い射影を UI スレッドの外で実行する

デスクトップが持つ五つの表示値型と、Swift と Kotlin が持つ会話行とタスク一覧の射影を、core の射影に統一する。
射影は `RenderedConversation` と同じ規律で、入力の参照が同一なら前回の値をそのまま返す。
会話の行と Markdown のような重い射影は Store のワーカーで実行し、派生した塊として発行する。
三つのアプリは同じ値を同じタイミングで受け取る。

### 3.3 デスクトップ：Desktop を独立したエンティティの木に置き換える

`Desktop` は廃止し、次のエンティティに分ける。
各エンティティは自分が描く部品の状態を所有し、自分が参照する塊だけを観察する。

- **ウィンドウ**：サイドバーの開閉、タブ、パネルの開閉と配置だけを持つ。子はすべて `cached` で置き、スナップショットやフレームごとの変化で描き直す要素を持たない。
- **サイドバー**：一覧、ナビゲーション、接続を観察する。行は仮想化する。ドラッグ状態は自分で持つ。
- **ヘッダー**：ナビゲーションと一覧の題名を観察する。
- **会話**：自分の会話の参照、入力の保留、自分に関係する操作キーを観察する。タイムライン、Markdown キャッシュ、選択範囲、質問への回答欄を所有する。
- **入力欄**：自分の下書き、カタログ、接続を観察する。テキスト状態、補完、音声入力、モデルと権限のポップオーバーを所有する。
- **ワークベンチ**：ワークスペースとパネルを観察する。ファイル探索、編集、ブラウザ、ターミナル、差分を所有する。
- **設定**：ページごとにエンティティを作り、アカウント、ワークツリー、接続のフォームを所有する。
- **通知**：範囲ごとのエラーを表示する。

操作は、自分の状態を変えるか、共有の `Arc<Store>` に `Intent` を直接 dispatch するかのどちらかにする。
別のエンティティへの UI 上の作用（パネルを開く、選択範囲をサイドチャットへ送る）は GPUI のイベントでウィンドウへ上げ、ウィンドウが子を操作する。
`WeakEntity<Desktop>` と、ビューから Desktop の文脈を借りる描画はなくなる。

毎フレームの処理はアニメーションを持つ末端のエンティティに閉じる。
`activity.rs` の別レイヤーはそのまま使う。

### 3.4 共通クライアント：ペイン

2026-10-04 の計画 4.3 節のペインを実装する。
ナビゲーションとワークスペースの選択はペインごとに持ち、会話のキャッシュ、購読、下書きはペインをまたいで共有する。
デスクトップのサイドチャットは同じ Store の二つ目のペインになり、二つ目の `Desktop`、Store、接続は削除する。
iOS のサイドチャットも同じペインを使い、ナビゲーションを一時的に切り替えて戻す実装を削除する。

### 3.5 モバイル：塊ごとの観察対象に分ける

iOS の `AppViewModel` は、接続、タスク一覧、会話、入力欄の四つの観察対象に分け、それぞれを core の塊の報告で更新する。
各画面は自分が描く観察対象だけを受け取る。
Android は `CompositionLocal` で配る一つの `snapshot` をやめ、塊ごとの状態に分ける。

iOS の会話画面は遅延描画に戻す。
`1acdd0298` が `VStack` に置き換えた理由（表示範囲に限った文字描画の計測キャッシュとネイティブ選択の保持）が `LazyVStack` と両立するかは、段階 5 の開始時に実機で確かめる。
両立しない場合は、その制約を本計画の未決事項に残し、所有者に選択を求める。

### 3.6 検証の規則

描画の孤立を、個別の「〜は Desktop を通知しない」テストではなく、一般則として検証する。

- 入力欄に N 文字打つと、入力欄のエンティティだけが描き直される。
- 会話への配信は、会話のエンティティと、一覧が変わった場合のサイドバーだけを描き直す。
- ウィンドウのルートは、レイアウトの変化がない限り描き直されない。
- 入力がなく実行中のタスクもない区間で、フレームは止まる。

これらは GPUI のテスト支援で描画回数を数えて確かめ、既存の個別テストは置き換える。
`desktop.frames` の診断ログは残し、段階ごとに 2.7 節の表を取り直す。

## 4. 採用しない仕組み

- 塊ごとの reducer と塊ごとの永続化。一回の確定を保つ。
- 汎用のリアクティブ基盤やシグナル。GPUI の `observe` と `Arc` の同一性で足りる。
- UI スタックの置き換え。Rust の core とネイティブ UI を保つ（2026-10-27 の決定）。
- Host の変更。Host の会話記録は別の決定で進んでいる。

## 5. 2026-10-04 の計画からの変更

次の二点は、その計画の記述を変える。
所有者の承認を要する。

- **塊ごとの変化の報告**：計画 4.3 節は「まとまりが個別に反応したり個別に保存したりする仕組みは作らない」と定めた。本計画は確定と保存を一つに保ちつつ、確定後の報告だけを塊ごとにする。報告を塊ごとにしなければ、各クライアントが変化の判定を再実装することになり、2.1 節の五つの手書き判定がその帰結である。
- **段階の順序**：計画の段階 8（Snapshot の構成、ペイン）と段階 9（画面の表示値）は、Host 側の段階 5 から 7 のあとに置かれていた。本計画はこれらをクライアント側で先に進める。Host の会話記録の決定（2026-11-02）が別に進んでいるため、依存は残らない。

## 6. 段階

各段階は、その時点で止めても製品として動く単位にする。
段階ごとに、削除する旧経路と、維持する受け入れ条件のテストを開始時に列挙する。

### 段階 1：塊ごとの発行

1. `Snapshot` を 3.1 節の塊で構成し、確定後の同一性比較と報告を一つのマクロで実装する。
2. デスクトップのサブビューは Desktop ではなく自分の塊を観察する。`general_snapshot_changed` を削除する。
3. モバイルは `SnapshotChanges` の代わりに塊の報告を受ける。`list_unchanged`、`conversation_unchanged`、`publication_key` を削除する。

完了条件：表示と操作は変わらず、入力欄への打鍵と会話への配信で、サイドバーとワークベンチの表示値が作り直されない。

### 段階 2：デスクトップのエンティティの木

サイドバー（仮想化を含む）、入力欄、会話、ワークベンチ、設定、ヘッダーの順に、状態と操作を Desktop から各エンティティへ移す。
一つ移すごとに、対応する `impl Desktop` ブロックと `WeakEntity<Desktop>` の参照を削除する。
最後に Desktop をウィンドウに縮め、名前を変える。

完了条件：3.6 節の四つの規則がテストで成立し、2.7 節の表でルートの paint 回数が、レイアウト変化の回数と一致する。

### 段階 3：core の表示値と重い射影の移動

デスクトップの五つの表示値型と、Swift と Kotlin の会話行とタスク一覧の射影を core の射影に置き換え、重い射影を Store のワーカーへ移す。

完了条件：三つのアプリが同じ表示値を受け取り、各アプリの重複した射影が削除されている。

### 段階 4：ペイン

ナビゲーションをペインごとにし、サイドチャットを二つ目のペインにする。
二つ目の Desktop、Store、接続と、iOS のナビゲーション切り替えを削除する。

完了条件：二つのペインで別々の会話を開き、片方の操作がもう片方の描画を起こさない。両方の下書きが保たれ、再接続後に両方が回復する。

### 段階 5：モバイルの観察対象の分割

iOS の `AppViewModel` を四つに分け、Android の `CompositionLocal` を塊ごとの状態にする。
iOS の会話画面の遅延描画を 3.5 節の手順で確かめて戻す。

完了条件：会話への配信でタスク一覧の画面が再評価されず、長い会話を開いたときに表示範囲外の行のレイアウトが走らない。

## 7. 進め方

- 作業は現在のタスク用ワークツリーのブランチで行い、他セッションの未コミット作業を保持する。
- 各段階の終わりに共通ユニットテストをビルダーで実行し、影響するアプリの受け入れテストは CI で確認してから報告する。
- main への統合は、段階ごとに所有者の確認を取ってから行う。
- 稼働中の Host は本計画では置き換えない。
